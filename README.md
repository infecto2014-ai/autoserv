# CRM автосервиса

Русскоязычная CRM TOP-СЕРВИС. Текущий рабочий сценарий облачной версии: одна форма приёмки → осмотр и согласование → ремонт → выдача с актом PDF → оплата, включая погашение долга после выдачи. Исходники облачного Worker/D1/React находятся в [cloud/](cloud/README.md); первоначальный Next.js/PostgreSQL вариант и Windows-запуск сохранены отдельно.

Переработка 21.11.2026 выполняется по [утверждённому описанию](docs/superpowers/specs/2026-11-21-top-service-workflow-design.md). Фактическая готовность и проверки этапов указаны в [PROGRESS.md](docs/PROGRESS.md).

Требования: [TASK.md](TASK.md). Правила разработки: [AGENTS.md](AGENTS.md). **Фактический статус и результаты проверок:** [docs/PROGRESS.md](docs/PROGRESS.md). Наличие команды или файла конфигурации само по себе не означает, что проверка уже выполнена.

## Временная облачная CRM

Рабочий закрытый экземпляр: https://autoserv-infecto2014.futureoleander4.chatgpt.site. Вход — тем же аккаунтом ChatGPT, которому принадлежит Site. Для этой версии не нужны Docker или установка на ПК.

Облачный вариант находится в [cloud/](cloud/README.md): сервер Cloudflare Worker, постоянная D1 (SQLite), сохранённые PDF и native ChatGPT auth. Локальный Next.js/PostgreSQL вариант ниже сохранён. Базы раздельные, существующие локальные данные автоматически не загружаются. GitHub хранит исходники; работающая CRM размещена на Sites.

## Windows: запуск двойным щелчком

Для автономной работы на своём ПК используйте [README-WINDOWS.md](README-WINDOWS.md): `Setup-Windows.cmd` один раз, затем `Start-Windows.cmd`. Интерфейс открывается на `http://localhost:3000`, данные хранятся в локальной PostgreSQL. Интернет нужен для первоначальной установки.

## Локальный запуск

Нужны Node.js 22.12+ (22/24), npm, Docker с Compose. Версии зависимостей закреплены в `package-lock.json`.

```bash
cp .env.example .env
```

Заполните `.env`:

- `POSTGRES_PASSWORD` — собственный пароль PostgreSQL. `DATABASE_URL` должен содержать этот же пароль в формате URI (специальные символы percent-encoded).
- `ADMIN_EMAIL`, `ADMIN_NAME`, `ADMIN_PASSWORD` — первый администратор; пароль не короче 12 символов. Готового стандартного пароля нет.
- `APP_ORIGIN=http://localhost:3000` — точный origin браузера; при обращении по другому имени укажите его явно.
- `SERVICE_NAME` — название сервиса; `TIMEZONE=Europe/Kaliningrad` — отображение времени. Даты в базе хранятся в UTC.

```bash
npm ci
docker compose up -d --wait db
npm run db:migrate
npm run db:seed
npm run dev
```

Откройте `http://localhost:3000` и войдите данными `ADMIN_EMAIL` / `ADMIN_PASSWORD`. Seed подготавливает первого администратора и каталог осмотра; рукописные цены с фотографии не используются как прайс-лист. Повторный seed сохраняет пароль существующего администратора, настройки и изменённые позиции каталога; клиентов и заказы он не создаёт.

PostgreSQL публикуется только на `127.0.0.1:5432`, данные находятся в Docker volume. `docker compose stop` сохраняет базу. `docker compose down -v` удаляет volume вместе с данными — для обычной остановки эта команда не нужна. Ошибка подключения обычно означает несовпадение пароля/URI, занятой порт или ещё не готовую БД. Изменение `POSTGRES_PASSWORD` в `.env` не меняет пароль уже инициализированного volume автоматически.

Production-режим в выбранной локальной среде:

```bash
npm run build
npm start
```

## Проверки

Для PDF-тестов нужен Poppler: команды `pdfinfo`, `pdftotext`, `pdffonts` должны быть в `PATH`. На Debian/Ubuntu пакет называется `poppler-utils`, на macOS — `poppler`. Для самого приложения и генерации PDF Poppler не нужен.

```bash
npm run lint
npm run typecheck
npm test
npm run build
npx playwright install chromium
npm run test:e2e
```

Интеграционные и E2E проверки выполняйте **только на отдельной тестовой БД с синтетическими данными**. Защитная проверка требует, чтобы имя базы в `DATABASE_URL` оканчивалось на `_test` (например, `sto_crm_test`). `DATABASE_URL` для тестов задаётся в окружении процесса; она имеет приоритет над локальным `.env`. Подготовьте тестовую БД, выполните для неё `npm run db:migrate` и `npm run db:seed` с отдельными `ADMIN_*`, затем запускайте проверки с теми же переменными. Для запуска интеграционных тестов задайте `RUN_DB_TESTS=1`; без этого флага они пропускаются. Playwright запускает production-сервер `npm start` на порту 3000 после предварительной сборки. Локально допускается повторное использование уже запущенного сервера; убедитесь, что он подключён к той же тестовой БД.

GitHub Actions выполняет установку зависимостей, миграции, seed, lint, typecheck, Vitest, сборку и Playwright с временным PostgreSQL. Все заданные в CI реквизиты синтетические, предназначены только для одноразовой тестовой среды. Workflow не размещает приложение и не обращается к рабочей базе.

## Резервное копирование и восстановление

Скрипты работают с сервисом `db` в `compose.yaml`, используют штатные `pg_dump` и `pg_restore` PostgreSQL. Запускайте из checkout с корректным `.env`.

```bash
bash scripts/backup.sh
# или указать новое имя:
bash scripts/backup.sh backups/before-update.dump
```

Архив PostgreSQL в custom-формате содержит данные CRM, PDF и активные сессии. Он создаётся с правами владельца, проверяется через `pg_restore --list` и не перезаписывает существующий файл. Держите копии вне git и переносите проверенные архивы в выбранное защищённое хранилище. Volume PostgreSQL не заменяет резервную копию.

Восстановление требует явного флага `--replace`. Перед восстановлением остановите процессы CRM, которые могут писать в базу, и сделайте актуальную копию. Лучше сначала проверить архив в отдельной тестовой установке.

```bash
bash scripts/restore.sh --replace backups/before-update.dump
```

Скрипт проверяет наличие, непустой размер и читаемость архива до изменений. Восстановление объектов из архива выполняется транзакционно с остановкой на первой ошибке; без `--replace` операция не начинается. Системные базы `postgres`, `template0`, `template1` запрещены. Дополнительные объекты, отсутствующие в архиве, не удаляются; для точного восстановления используйте отдельную чистую базу. После восстановления проверьте вход, историю автомобиля и открытие сохранённого PDF.

## Docker и будущее размещение

`compose.yaml` запускает только PostgreSQL. `Dockerfile` готовит образ приложения обычной многоэтапной сборкой (`npm ci`, `next build`, `next start`), с Prisma и локальными шрифтами. Процесс работает от пользователя `node`; `.env`, дампы и агентские инструменты в образ не попадают.

```bash
docker build -t sto-crm:local .
```

В текущей среде сборка Docker-образа **не завершена**: Docker VFS исчерпал доступный дисковый лимит. Работоспособность готового контейнера не подтверждена; успешная локальная production-сборка Next.js и проверки Compose/backup/restore рассматриваются отдельно. Повторить проверку образа нужно в среде с достаточным свободным диском.

Если сеть сборки требует корпоративный прокси, передайте стандартные `HTTP_PROXY`/`HTTPS_PROXY` как build arguments. Дополнительный доверенный CA можно передать через BuildKit `--secret id=build_ca,src=/путь/к/ca.pem`: Dockerfile использует его только во время `npm ci` через secret mount. Сертификат и настройки не копируются в runtime image; проверка TLS не отключается.

При выборе размещения потребуется передать runtime-переменные, обеспечить PostgreSQL, выполнить миграции отдельным шагом, настроить HTTPS и резервные копии. Миграции и seed намеренно не запускаются автоматически при старте каждого экземпляра. Никакой платный сервис или публичная публикация этой конфигурацией не создаётся.
