# План реализации CRM TOP-СЕРВИС

> **Для агентов:** обязательный навык `superpowers:subagent-driven-development`; задачи выполняются последовательно, с независимой проверкой каждой задачи и итогового изменения. Шаги отмечаются `- [ ]`.

**Цель:** дать приёмщику рабочий путь от одной формы приёмки до согласованного ремонта, выдачи с актом, учёта оплат и повторного обращения.

**Архитектура:** расширяем существующие Worker/D1/React в `cloud/`. Финансовая логика общая и чистая; серверные изменения атомарны, PDF хранит неизменяемый снимок. UI использует реальные API.

**Стек:** TypeScript, React 19, Cloudflare Worker/D1 SQLite, pdf-lib, Vitest, существующий esbuild. Новые библиотеки без необходимости не устанавливать.

**Спецификация:** `docs/superpowers/specs/2026-11-21-top-service-workflow-design.md`.

## Общие ограничения

- Приоритет прямых ответов пользователя над старым TASK.md. Работаем в `/workspace/sto-crm-topservice`, ветка `feat/top-service-workflow`.
- Деньги — целые копейки; скидка в рублях только на согласованные работы. Несогласованное и детали клиента не увеличивают итог.
- Мастера — справочник назначения, сейчас без отдельного входа. Серверная авторизация и закрытый доступ сохраняются.
- Приёмка требует марку, телефон, жалобу; имя/VIN/госномер/модель/пробег/мастер необязательны.
- Четыре группы не пересекаются. Выдача допускает долг, выданный заказ редактируется, PDF версионируется.
- TOP-СЕРВИС; Калининград, ул. Стрелецкая, д. 8, корп. 2; +79114709360; Europe/Kaliningrad.
- Существующие данные, долги и акты сохраняются. Старое согласие и даты платежей не выдумываются.
- Коммиты и push разрешены пользователем. Ни один исполнитель не делает push; контроллер отправляет проверенный результат.
- Нельзя коммитить local node_modules, .env, PDF/БД с клиентскими данными, секреты. Не выполнять изменения production БД в рамках локальных проверок.

## Особое внимание при проверке

1. Повтор запроса приёмки/платежа/выдачи после потерянного ответа не дублирует записи: задачи 2/3.
2. Предоплата до оценки, бесплатная диагностика, копеечное округление и скидка на всю работу не теряют деньги: задачи 1/2.
3. Старые заказы без согласий сохраняют исходные долги, документы и неизвестные даты оплат: задачи 1/2.
4. Изменение состава после выдачи/оплаты не переписывает прошлые распределения/PDF и учитывает переплату: задачи 2/3.
5. Общий телефон и машины без VIN/номера не сливаются; границы календарного периода — Калининград: задачи 2/4.

**Интерфейсы:**
- `Approval = 'PENDING' | 'APPROVED' | 'DEFERRED'`; строки получают `approval`, `completed`, `partSource: 'SERVICE' | 'CUSTOMER'`.
- `calculateWorkflowTotals(lines, discountCents, paidCents, finalized?)` возвращает существующие Totals плюс `overpaidCents`; финализированный состав считает только выполненные согласованные позиции.

Старые таблицы не сбрасываются, старые Document kind допускаются; итоговый акт может использовать существующий WORK_ORDER с новым шаблоном/снимком.

### Task 2: рабочие API приёмки, заказов, оплат и статистики

**Файлы:** worker/{intake,payments,overview}.ts, worker/orders.ts, api.ts, crud.ts, auth.ts; целевые tests/intake.test.ts, payments.test.ts, overview.test.ts, orders.test.ts, crud.test.ts и workflow.test.ts при необходимости.

**Потребляет:** результаты задачи 1, существующие `guarded`, `mutateOrder`, `Context` и серверную авторизацию.
**Производит публичный контракт:**
- `POST /api/intake` — `{requestId, make, model?, phone, name?, vin?, plate?, mileage?, masterId?, complaint, customerId?, vehicleId?}` → OrderDetail. Один атомарный запрос создаёт/использует выбранные записи; неоднозначные совпадения не объединяются. Повтор requestId возвращает тот же заказ; другая нагрузка с тем же ключом — 409.
- `GET /api/overview?from=YYYY-MM-DD&to=YYYY-MM-DD` → `{counts:{active,approval,ready,completed}, money:{laborCents,partsCents,totalCents,unallocatedCents,debtCents}, ...}`. Текущие группы/долги не скрываются датами; completed — по выдаче, деньги — по платежу, период включителен в локальных датах.
- `POST /api/orders/:id/payments` — `{requestId,version,amountCents}` → OrderDetail; возврат — тот же маршрут с `kind:'REFUND',relatedPaymentId,reason`. Платежи отражаются в OrderDetail.payments. Распределения сохраняются после первого расчёта.
- `POST /api/orders/:id/review-finances` — `{version}` подтверждает проверку и перевод старого заказа на новый расчёт с аудитом; менять строки/скидку старого расчёта без проверки нельзя.
- Существующий PATCH заказа, PUT строк, осмотр и создание строк используют согласование/выполнение/источник. Изменение согласованной цены/количества требует нового согласия, явное подтверждение передаётся отдельным действием/запросом. Выданный заказ редактируется; закрытие DELIVERED через обычный PATCH запрещено — задача 3 реализует выдачу с документом.
- GET заказов поддерживает `debtOnly=1` и фильтр дат; база клиентов/машин — поиск включая марку/модель/телефон/заказы по периоду. Добавление мастера требует имени, без обязательного email/новой учётной записи.
- CSV маршрут `/api/orders/export` больше не выдаёт данные.

**Производит:**
