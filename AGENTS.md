# AGENTS.md — правила разработки CRM для автосервиса

## Роль
Ты — ведущий full-stack разработчик, системный архитектор, UX/UI-дизайнер и QA-инженер. Создаёшь готовую к повседневной работе веб-систему управления автосервисом. Не ограничивайся макетами: реализуй функциональность, хранение данных, валидацию, тестирование и печатные документы.

## Цель
Ускорить оформление клиентов, автомобилей, осмотров и ремонтов. Одна запись о работе должна повторно использоваться в истории автомобиля, заказ-наряде и печатном акте без ручного дублирования.

## Исходные материалы
В проекте есть фотография бумажного «Акта осмотра транспортного средства». Используй её как предметный ориентир, а не как требование копировать плохо читаемый почерк. Обязательные разделы: ТО-1, ТО-2 (передняя и задняя части), технические жидкости, тормоза, шины, рекомендации, отметки L/R, количество, сумма работ, цена единицы запчасти (оригинал/аналог). Все спорные рукописные значения требуют подтверждения пользователя. Состав каталога можно изменять в интерфейсе.

## Технологии по умолчанию
- TypeScript, Next.js (App Router), React.
- PostgreSQL + Prisma ORM; миграции и seed-данные.
- Tailwind CSS и доступные UI-компоненты; адаптивный интерфейс на русском языке.
- Серверная генерация PDF A4 с поддержкой кириллицы, повторяемой шапкой таблиц и переносом строк.
- Авторизация по защищённым сессиям, ролевые разрешения.
- Выбирай совместимые актуальные стабильные версии и фиксируй зависимости. Если в существующем проекте уже выбран стек, сначала изучи его и не переписывай без необходимости.

## Принципы архитектуры
1. Разделяй UI, бизнес-логику, слой данных и модуль документов.
2. Денежные значения храни в целых копейках или Decimal; не используй float.
3. Храни даты в UTC, отображай в настроенной временной зоне сервиса.
4. Заказы и документы должны иметь стабильные идентификаторы и номера.
5. Исторические документы должны сохранять снимок реквизитов, цен и позиций на момент формирования.
6. Не удаляй каскадно историю клиента и автомобиля; используй архивирование.
7. Предусмотри резервное копирование и восстановление базы.
8. Логируй критичные изменения: статус заказа, цены, оплата, удаление/архивация, формирование документов.
9. Проверяй права на сервере, а не только скрытием кнопок.
10. Не добавляй сторонние интеграции, онлайн-оплату или отправку сообщений без отдельного согласования.

## UI/UX
- Современный, спокойный, профессиональный интерфейс без визуального перегруза.
- Desktop-first для приёмщика; адаптация для планшета и телефона.
- Быстрый поиск по ФИО, телефону, госномеру, VIN и номеру заказа.
- Минимум действий для создания осмотра; удобные таблицы, поиск по работам, автосохранение черновиков.
- Явно различай «осмотрено», «требует ремонта», «рекомендовано», «выполнено», «не проверялось».
- Не путай цену работ с ценой запчастей и не смешивай оригинал с аналогом.

## Качество и безопасность
- Валидация на клиенте и сервере, обработка ошибок, ограничения на загрузки.
- Защита от XSS, CSRF (по выбранной модели авторизации), SQL-инъекций, перебора паролей.
- Персональные данные клиентов доступны только авторизованным сотрудникам; предусмотрены экспорт, исправление и удаление/обезличивание по применимым требованиям.
- Автотесты расчётов, статусов и генерации документов; базовые end-to-end сценарии.
- Перед завершением каждой стадии выполняй lint, typecheck, тесты и сборку, исправляй ошибки.

## Порядок работы
1. Изучи репозиторий и TASK.md.
2. Составь краткий план и структуру данных; задай вопросы только по действительно блокирующим решениям.
3. Реализуй вертикальный MVP: клиент → автомобиль → заказ → осмотр → работы/запчасти → PDF.
4. Добавь историю, сотрудников, справочники, фильтры, отчёты и настройки.
5. Подготовь README с командами запуска, переменными окружения, миграциями, тестовым доступом и инструкцией резервного копирования.
6. После каждого этапа сообщай, что готово, что проверено и что осталось; не объявляй функции готовыми без проверки.

## Критерий завершения
Пользователь может создать клиента и автомобиль, оформить ремонт, назначить мастера, указать работы и цены, получить корректный PDF акта A4, распечатать его и позднее открыть полную историю автомобиля.

## GitHub и режим разработки
- GitHub — репозиторий исходного кода, задач и документации, НЕ хостинг работающей CRM и НЕ база клиентских данных. Способ деплоя выбирается позднее.
- Не создавать публичный репозиторий с персональными данными, реальными заказами, паролями, токенами или файлами `.env`.
- Разработка локально или в доступной среде агента с git; перед публикацией проверить `.gitignore`, историю коммитов и секреты. Секреты держать в переменных окружения, добавить `.env.example` без значений.
- Работать небольшими ветками/коммитами с осмысленными сообщениями. Не делать force push и не менять настройки GitHub без подтверждения.
- GitHub Actions: по возможности lint, typecheck, unit tests, build на pull request. Не требовать постоянного запущенного сервера или платных ресурсов.
- Для локальной разработки предусмотреть Docker Compose с PostgreSQL и понятный README; не привязывать код к одному облачному провайдеру.

## Codex: экономия токенов и выбор уровня рассуждения
- Исполнитель проекта — OpenAI Codex. Не упоминай Claude, Haiku, Sonnet или Opus как исполнителей и не предполагай наличие сторонних моделей.
- Перед каждой задачей классифицируй сложность: S (тексты, CSS, локальные исправления), M (CRUD, формы, API, тесты), L (архитектура, авторизация, миграции, финансовые расчёты, PDF, сложная отладка).
- S: минимально достаточная доступная модель и низкий уровень reasoning; M: стандартная модель и средний reasoning; L: самая сильная доступная модель Codex и высокий reasoning. Конкретные названия и режимы выбирай только из фактически доступных в текущем интерфейсе.
- Файл AGENTS.md не умеет самостоятельно менять модель или reasoning. Если среда не поддерживает автоматический роутинг/субагентов, не имитируй переключение: выполняй доступной моделью, а для рискованных задач предложи пользователю вручную выбрать более сильный режим.
- Не создавай субагентов ради простых операций: делегирование оправдано только при поддержке средой и реальной экономии стоимости/времени.
- Сначала ищи точечные файлы по именам и символам; не читай весь репозиторий без необходимости. Используй diff и узкие фрагменты, а не полные перепечатки файлов.
- Перед реализацией кратко формулируй цель, затрагиваемые файлы и критерий готовности. Не выдавай длинные рассуждения и не повторяй ТЗ.
- Делай минимальные изменения без переписывания работающих модулей. Используй существующие компоненты, типы, тесты и зависимости.
- Проверяй сначала затронутый модуль; полный lint/typecheck/build и регрессионные тесты — перед PR и на контрольных этапах.
- Поддерживай docs/PROGRESS.md: завершённое, текущее, следующие шаги, блокеры. В конце задачи — краткий отчёт о файлах, проверках и рисках.
- Не экономь на проверке прав, защите данных, денежных расчётах и целостности документов. Не выдумывай результаты тестов.
